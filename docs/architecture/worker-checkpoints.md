# Worker checkpoint integration

**Design approved and planning closed, 26 November 2026.** See the [closure and remaining owners](../memory.md#worker-checkpoint-planning-closure--26-november-2026). [Agent recovery](agent-integration.md#persistent-recovery-and-concurrency), [standalone T07/T16](../implementation/standalone-agent.md#t07--outer-graph-private-wrappers-and-redis-projection), [storage](database-storage.md), [API](backend-api.md) and [workers](background-workers.md) own existing behavior. This guide owns the approved application-worker binding and acceptance contract. Existing recovery policy remains authoritative; design approval is not proof of implemented milestones.

## Existing decisions and observed implementation boundary

Reuse the independent agent's `build_graph(..., checkpointer: BaseCheckpointSaver, ...)`, `restore_run(run_id, ..., authority, checkpointer, config)` and same-run resume boundary. The standalone plan selects production RedisSaver, Redis 8 JSON/search, persistence and no TTL; fake/in-memory savers are explicitly offline tests. Use the same package with the application's Postgres authority adapter, not a Django-specific graph fork or live writable SQLite side ledger. Checkpoint `thread_id` is run_id, never Chat ID, WorkIntent ID or Celery task ID. Keep approved role/invocation/attempt child namespaces and the exact nine-field parent projection; scope, ownership and accounting remain authoritative domain records.

Focused source inspection found `runtime/redis_projection.py` with a separate RedisProjection/CheckpointRecord interface, a seven-day default TTL and JSON save/latest/index operations, alongside a broader runtime RunState container. Existing dependency metadata pins LangGraph 1.2.24 and langgraph-checkpoint-redis 0.6.0. These observations do not prove BaseCheckpointSaver conformance, strict nine-field graph projection, protected metadata, native graph recovery or real Redis readiness. Those are compatibility gates for the owning standalone/runtime implementation. Do not silently bless the TTL, serialize an arbitrary runtime container as the parent contract, substitute an in-memory saver or upgrade pinned packages to make worker integration appear complete.

## Selected integration and rationale

Use the maintained RedisSaver behind the independent package's guarded checkpoint/recovery adapter. The worker supplies claimed run scope, current domain OwnerFence, immutable configuration/manifests, Postgres authority and process-local saver lifecycle. Runtime builds the same graph/private handlers and reconstructs the next legal transition from committed records.

Use a small Postgres projection registry in the existing canonical record/delivery families. It records which checkpoint write corresponds to a committed run revision and compatible graph/schema/namespace manifest. Redis's raw latest pointer is not the adoption authority. Reuse already committed checkpoints when validated; rebuild missing/lagging/unusable projections from the ledger. This avoids copying another run, exposing arbitrary live time travel, or letting framework replay become another dispatch engine.

Checkpoint-only restore was already rejected because it cannot atomically preserve deletion, publication and shared accounting. Replacing Redis with PostgresSaver is outside this integration: Redis-backed standalone recovery is an approved requirement. A custom complete saver/runtime rewrite is not the default alternative; conform the existing selected stack or block the capability when a required guarantee cannot be implemented. This is not authorization to repair current source during planning.

## Binding records and runtime interfaces

| Binding | Required contract |
| --- | --- |
| Run binding | Project/Chat/run IDs, immutable source/basis/configuration refs, graph/checkpoint/state/codec/serializer manifest identities and logical namespace mapping. Record installed build identities, not whatever versions a current documentation page happens to describe. |
| Projection descriptor | Runtime descriptor ID, run_id, checkpoint_id and parent/child namespace refs, projected run_revision, triggering transition, writer generation, checkpoint/pending-write schema identity, protected payload/manifest digest and pending/verified/adopted/rejected/erase_pending disposition. Unique transition/projection mapping; repeat acknowledgment returns the original descriptor. |
| Projection delivery/write intent | Stable transition/attempt identity, expected run revision/current generation and scope/source dependencies; records write start, completion/readback, uncertainty and cleanup ownership. Cross-store write failure leaves a replayable pending item, not a rolled-back model/tool result. |
| Worker invocation | Resolve WorkIntent to the original run, acquire/reconcile domain ownership and call restore/resume with its exact authority/checkpointer/config. A Celery message cannot supply serialized RunState, a browser-controlled checkpoint_id or a trusted owner fence. |
| Restore result | Typed disposition: already terminal, still waiting, ready to advance, recovery/retirement pending, checkpoint unavailable or incompatible/integrity blocked; includes reconstructed projection and exact legal continuation refs only where usable. No side effect is performed merely by inspecting restore state. |
| Lifecycle | Create saver/Redis clients and DB connections after worker process start/fork, verify capabilities, use bounded operations and close/drain them on handoff/shutdown. Do not reuse inherited event loops/connection pools across processes or reconnect into a new run identity. |

Checkpoint metadata is separate from the nine parent fields. Serialize only explicitly allowed schema values and tagged canonical types; no pickle fallback, arbitrary class rehydration, credentials, full uploads or unbounded provider/tool histories. Runtime chooses trusted handler classes; checkpoint data cannot name a callable to execute. Private child history stays bounded and invocation-scoped and cannot become another Chat's context. Checkpoint source dependencies cover all material included in that projection; a checkpoint with removed dependencies is unusable even when an independently scoped completed answer still survives in the ledger.

## Worker entry and restore sequence

1. Validate and claim the durable WorkIntent under the worker contract. Resolve live Project/Chat/source/run state, original deadlines, cumulative charges, protected reserves, publication/wait/reply and unresolved operation records. Acquire/reconcile the current coordinator generation before any effect; reject duplicate live ownership.
2. If the ledger already has a terminal publication, return that identity under current access policy and repair delivery only. If it is still waiting without an accepted matching reply, return the same wait/card and release the worker. Neither path calls a model, recreates a question or starts analysis.
3. Check exact graph/checkpoint/codec/configuration compatibility and Redis capability. Resolve the ledger-registered checkpoint descriptor and read by its specific identity/namespace; do not blindly load Redis latest. A historical writer generation is provenance, not present permission: a validated old checkpoint can supply committed progress, but all current writes/effects require the new current fence.
4. Reconstruct the nine-field parent projection from authoritative immutable records, including canonical terminal siblings, active task/attempt mappings and exact review/wait/candidate lineage. Validate native pending writes against their task/attempt/invocation and committed outcome; no cached pending write can create eligibility by itself. Rebuild private contexts only from their committed bounded packets/history, not from another worker's memory.
5. Compare the saver projection with that reconstructed revision/control state. Adopt only compatible, authorized data; register a verified rebuilt projection when needed. A framework checkpoint after a ledger commit may be stale, but ledger-committed results remain reusable. Redis outage blocks ordinary new graph advancement; it cannot authorize a fallback unfenced runner.
6. Dispatch the next legal graph transition through existing runtime wrappers. A replayed node first resolves its committed invocation/outcome/handoff and returns that same result. Only absent, permitted work can reserve/dispatch new external effects; successful siblings, physical request settlement, review passes and publication are never repeated because a node body restarted.

## Projection write and concurrency

Commit each domain transition with a replayable projection-delivery record. Reserve the corresponding saver write under current source/run/owner guards; perform Redis I/O after releasing the DB transaction. Write/read back the exact checkpoint and protected metadata, including necessary child/pending-write dependencies. In a fresh short guarded DB transaction, verify the represented ledger revision and adopt the descriptor/acknowledgment. A lost acknowledgment repeats validation/adoption by identity. No two-phase transaction spans Postgres and Redis.

The guarded saver must prevent a stale generation or lower revision from becoming the selected projection. A late obsolete Redis write may not move the Postgres adoption pointer or authorize execution; readers resolve the adopted descriptor and recheck current authority. Index/latest/missing child/blob inconsistencies are rejected or reconstructed rather than treated as a complete checkpoint. A new owner may reuse valid previous-generation content under a new fence without changing run/thread/logical child identity. Exact guarded write, index, child/pending-write and deletion behavior must be proven on the pinned saver; no undocumented atomicity claim is made from its convenience API.

Use synchronous acknowledgment of required persistence boundaries before ordinary graph advancement/new effects; exact supported invocation/options must be verified against the locked SDK. Framework/Celery retry defaults cannot create extra model/tool requests. If a checkpoint write fails after a domain commit, preserve that commit and its charges, stop new ordinary effects and reconcile the pending projection. Do not refund a committed review pass, roll back a published result or make a model call to recreate an existing response. Already dispatched external work remains subject to its own recorded adoption/retirement policy.

Different private action branches retain independent namespace/expected-attempt identities while sharing the one coordinator and aggregate counters. Recovery of one failed branch cannot erase successful sibling outcomes. Adopted projection state and visibility/deletion checks follow the existing Project/source → run → child lock discipline and expected revisions. A Celery task acknowledgment or socket reconnect never selects a checkpoint.

## Clarification and same-run recovery

The ledger owns question generation slots, active question, wait expiry, one accepted reply and resume readiness. The graph interrupt is an execution hint only. Commit the exact waiting question/card and projection intention before exposing it; release worker/sandbox resources while the user waits. A failed Redis write does not undo an already committed card or prevent the API from storing a valid linked reply under current guards.

On accepted reply, one durable wake resumes the original run with its frozen basis plus that exact reply. A LangGraph resume value references the committed ResumeReceipt/question/reply identities; raw socket text cannot rewrite scope/configuration or bypass entry screening. On node re-entry read the accepted ledger handoff instead of regenerating the question or resubmitting a job. If the graph/checkpoint is missing, reconstruct that same state and resume readiness; if the reply remains absent, stay waiting. Expired/removed-source/stale questions cannot be revived. Analytical and entry-policy clarification remain separate chains.

Operational recovery reuses the original run and remaining budget/time; terminal publications remain terminal. A user Retry or automatic permitted worker reconciliation cannot fork historical checkpoints into live effects. Debug replay/fork is offline-only with external dispatch disabled; it is not an API feature or a route to a freshly funded run.

## Failure and compatibility matrix

| Condition | Required disposition |
| --- | --- |
| Missing/lagging checkpoint or absent child/pending write | Reconstruct from compatible committed records without model calls or replay of terminal operations, then write/read back and adopt a valid projection. Missing canonical inputs instead blocks recovery; no guessed replacement data. |
| Checkpoint ahead of ledger, wrong scope/namespace or conflicting digest | Deny adoption, quarantine its access-controlled descriptor and rebuild only from the ledger. Do not accept a saved success that the authority never committed. Quarantine is subject to the same deletion policy, not a forever content audit. |
| Redis unavailable/full or JSON/search/serializer capability missing | Block new ordinary graph effects, retain pending delivery/claims within finite bounds and expose recoverable checkpoint unavailability when legal. Existing committed result/card remains ledger-readable under access policy. No MemorySaver, TTL change or new run fallback. |
| Different graph/state/codec/handler version | Resume only under an explicitly verified compatibility manifest. Otherwise block with a bounded operational outcome. No latest-package upgrade, dropped state field or unsafe deserialization. |
| Worker dies after commit but before saver write/ack | New owner reconstructs the committed transition and repairs projection delivery. Already charged requests/passes and valid outcomes retain identity. |
| Worker dies during external execution | Reconcile recorded responses/operations first; unknown calls retain maximum exposure and uncertain SQL/Python work retains retirement barriers. An expired lease or missing checkpoint never proves previous execution ended. |
| Duplicate linked reply/recovery/message | Resolve the same committed handoff and WorkIntent; no second question, resume, coordinator, publication or allowance. |
| Publication committed, checkpoint/socket delivery incomplete | Retrieve/replay that publication identity after authorization. Do not render a new candidate or require a model/Reviewer pass to repair delivery. |
| Source/Chat/result/Project deletion during restore/write | Revoke in the authority, deny adoption/use, fence late writers and enqueue all affected projection/private-history/pending-write erasure. Cleanup completion requires handling in-flight/late writes, not just deleting a latest pointer once. |

Persist graph/state/serializer/namespace manifests on run admission; worker deployment checks compatibility before claiming resumable work. If a future deployment changes them, drain/quiesce affected writers and use an explicit verified migration or keep the compatible old runtime available. This is controlled deployment, not automatic arbitrary checkpoint conversion. Unmigratable retained runs receive the approved bounded incompatibility result rather than silent fresh analysis. The existing SQLite-to-Postgres authority switch preserves these same descriptors/identities and does not dual-write.

## Retention, deletion and resources

Keep the selected full RedisSaver history persistent with no automatic TTL initially, matching standalone T07; do not adopt the separate helper's seven-day default or switch to a shallow saver. Apply explicit finite storage/record/connection limits. Reaching capacity blocks dependent new effects and exposes a bounded operational condition; it does not silently evict unverified active checkpoints. Compaction beyond user/dependency deletion needs its own verified policy and cannot erase ledger evidence or reset budgets.

Checkpoint storage remains private in its own Redis database/namespace, separated from Celery broker and Channels keys. Hashes/IDs and bounded private history follow ownership/source deletion policy. Store no hosted trace copy of checkpoint payloads. Revoke access immediately in Postgres; then the maintenance process erases all affected root/child checkpoint, blob/write/index and private-history keys using scoped saver operations and verified inventories. No service-wide FLUSH operation or unknown-prefix deletion is allowed.

Track write attempts before I/O and retain erasure/late-writer obligations until writers are reconciled/quiesced and all related keys are verified absent. The pinned guarded saver must prove a stale writer cannot recreate a usable checkpoint after revocation, and that cleanup catches any late private bytes before reporting complete. If writer/deletion fencing cannot be enforced with the chosen build/wrapper, keep the capability blocked; a successful `delete_thread` call alone is not full race proof. Deletion never recreates content from a stale checkpoint or uses a restored Redis backup to reverse a tombstone.

| Slice | Required evidence |

| C3 replay-safe effects and waiting | Interrupt before/after committed tool/model result and exact waiting-card/reply handoff; count actual scripted transport calls, preserve successful siblings and review-pass reservations. A restarted node cannot resubmit committed effects. |
| C4 fencing, deletion and outages | Stale concurrent owner/saver writes, partial root/child/index writes, Redis outage/full storage/restart, wrong schema/namespace, invalid Unicode/tags and malicious serialized data; source/Chat/result/Project deletion at every save/read/adopt/cleanup boundary. | C5 application recovery handoff | Real Celery process interruption/redelivery with same Postgres authority and Redis saver, bounded recovery, missed WebSocket updates and original waiting reply. Use independent deterministic fixtures and trusted scripted model/sandbox transports to isolate persistence behavior; real external execution/retirement proof keeps its separate authorization/gates. Record actual call/pass/accounting counts, process identities, schema/build manifests and crash point for reproducibility, without checkpoint/question/source payloads in hosted traces. Exact connection/persistence/lease/timeout/resource settings and a compatible built manifest are implementation enablement gates. No Redis/Celery service, checkpoint test, migration, dependency update or live/paid execution ran during this planning phase.
