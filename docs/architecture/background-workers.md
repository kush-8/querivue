# Background workers and job delivery

**Design approved and planning closed, 25 November 2026.** See the [closure and remaining owners](../memory.md#background-worker-planning-closure--25-november-2026). [Storage](database-storage.md), [API/WebSocket](backend-api.md) and [agent authority/recovery](agent-integration.md#persistent-recovery-and-concurrency) retain their approved contracts. This phase does not implement workers, complete standalone milestones or authorize service/account/network effects.

## Transport choice and Cloudflare comparison

The user selected Celery with the existing Redis service for the initial local application after reviewing Cloudflare. The approved worker layout runs it in Linux containers under the already planned Compose environment. Redis remains required for checkpoints and Channels whether or not the job broker moves elsewhere. Celery's Windows host support is not a supported deployment target; this recommendation does not require moving the repository or editor off Windows.

| Approach | Fit and practical tradeoff |
| --- | --- |
| Celery + local Redis | Keeps Django/agent execution, database and files in the existing local environment. No cloud queue account or Internet dependency for delivery. Adds Celery process/configuration/dependencies, but does not add another broker service. Postgres intents and guarded runtime calls still supply correctness. |
| Cloudflare Queues + local Python HTTP-pull consumer | Viable alternative broker: local workers pull and acknowledge over outbound HTTPS, so Django need not expose a public callback/tunnel. Retains local CPython, Postgres and file access. Requires a queue transport/consumer adapter, cloud credentials, account/rate/free-entitlement verification, Internet availability and external metadata governance. It does not remove Redis checkpoints/Channels or make the local worker execute while the machine is off. Implement this instead of, not alongside, the initial Celery transport if selected. |
| Cloudflare Workers hosting the coordinator | A separate runtime/deployment change. Python Workers run through Pyodide/WebAssembly in isolates, rather than the existing native Python process/container contract. Workers' CPU/memory limits and Django/agent/package/database/file compatibility need their own design and measured proof. Do not assume the CLI, Celery or generated execution environment can be copied there. No hosted/public deployment or infrastructure migration follows from considering it. |

Cloudflare's published Queues Free allowance is 10,000 standard operations/day with non-configurable 24-hour retention. A small normally delivered message generally uses write/read/delete operations; retries and dead-letter handling add work. These are dated public plan facts, not this account's verified entitlement or a guarantee of a zero bill. If Cloudflare is selected, preserve the zero-paid-spend boundary, verify actual account limits/enforcement and forecast all operation scopes before any authorized live test. Queue IDs/digests are governed metadata, not presumed anonymous: send only bounded opaque work/delivery identities, no questions, rows, prompts, source names, files, responses or credentials. Source removal must also cover owned remote messages/DLQ metadata or let them expire under an explicitly approved policy while denying all access/execution immediately.

Cloudflare was considered but is not selected for this phase. Its comparison is retained as decision rationale, not an enabled fallback or an implementation task.

Cloudflare Queues provides at-least-once delivery and HTTP pull visibility leases; duplicate delivery still needs the same database claims/fencing. Expired, exhausted or lost cloud messages cannot be the sole copy of pending work. Keep the work-intent boundary below independent of the broker, but build/test only the chosen initial adapter. Using Cloudflare Queues does not require deploying a Cloudflare Worker for this pull-consumer design. The existing Workers AI model-provider approval is unrelated to job-broker/runtime selection.

## Responsibilities and process layout

The HTTP/WebSocket process validates and commits commands/receipts. It never starts an unmanaged execution thread. The domain transaction inserts a durable WorkIntent and replay/delivery intentions with its accepted state. A separate maintenance/dispatcher process publishes pending work outside transactions, reconciles expired claims and performs bounded delivery/cleanup sweeps. Losing that process delays work, not its durable identity; it restarts from Postgres. Initial maintenance uses the existing management-command/service boundary, not a second workflow engine, database scheduler extension or independent queue authority.

Use two worker roles: a control worker for bounded entry screening and short control handoffs, and an execution worker for inspection/preparation and admitted analytical run continuations. Start with one execution slot as an approved conservative local development candidate; retain the approved runtime's bounded in-run specialist branches, gated on actual resource proof. Separate control/maintenance from long analysis so clarification intake, deletion and delivery reconciliation are not stuck behind one run. Global/project model, run, sandbox and admission accounting still constrains all roles together; process separation cannot create additional allowances. No global Chat execution lock is introduced.

Run the same independent agent package through the application Postgres adapter; no separate agent SQLite store remains writable in application mode. Worker containers mount the approved shared file volume with required controller access. Generated SQL/Python and upload parsing keep their approved execution isolation boundaries; a Celery worker is not that sandbox. API/worker/maintenance processes have finite memory/CPU/connection caps, non-root runtime users and no public broker/worker control ingress. Credentials stay in runtime environment/secret configuration and never in task payloads or recorded request hashes.

## Durable work records and interfaces

Extend the existing delivery/ownership record families rather than replace the agent ledger:

| Record/interface | Contract |
| --- | --- |
| WorkIntent | Immutable work_id, kind/schema version, Project and exact subject identity (intake, preparation attempt, run continuation or reconciliation), triggering transition/revision, manifest/config ref, creation/due/expiry bounds and payload digest. Unique scoped logical wake key prevents a duplicate submission/reply/recovery from creating duplicate work. Mutable disposition is pending/dispatched/claimed/waiting_retry/blocked/done/obsolete with expected revision and bounded transport counters. This is delivery state, not an alternate public run state. |
| DeliveryAttempt | WorkIntent ref, unique delivery_id/transport task identity, publish attempt, immutable envelope digest, publisher claim/generation/expiry and sent/unknown/observed disposition. Publishing is not proof of execution or completion. Domain attempts, model physical requests and delivery attempts are distinct counters. |
| WorkClaim | Current worker identity/generation/lease and work revision. Run/preparation/intake domain ownership and OwnerFence remain authoritative for effects. A broker message cannot supply a trusted lease or override a current owner. |
| WorkEnvelope | Strict allowlisted version/kind plus work_id and delivery_id only. Load and validate original inputs/configuration/scope from Postgres; reject forged/missing/unsupported/conflicting records. JSON only; no pickle, arbitrary callable names, client-supplied Python or stored credentials. Broker access is private and least-privilege. |
| Executor | `execute_claimed(work_id, claim) -> WorkDisposition`: load exact typed subject, acquire/reconcile its domain owner, invoke the existing operation boundary, and commit terminal/wait/retryable/blocked disposition. Return only IDs/diagnostics needed by delivery; domain outcomes remain canonical records. Exact Python module names are implementation choices. |
| Dispatcher/reconciler | Claim/publish due work; inspect unresolved delivery/current claims; reconcile progress/retirement; schedule another permitted wake only under unchanged scope/accounting. Public result/status comes from the ledger, never Celery AsyncResult or a cloud message body. |

Keep these rows under Django migrations and the approved same-Project ownership constraints and lock order. All claims, wake keys, revisions and state transitions use short transactions. Determine earlier-tier guards before acquiring child locks; no broker, provider, file transfer or Redis call is awaited inside them.

## Commit, delivery, execution and acknowledgment

1. **Commit command and intent together.** A durable receipt is returned only after both commit. An on_commit callback may wake the dispatcher; its loss cannot lose the intent. Queue admission is finite and does not reserve an unlimited backlog of already expiring/funded runs.
2. **Claim a publish attempt.** Under guards allocate a delivery identity and finite publisher lease/counter; release the transaction before publishing. An ambiguous publish response records uncertainty. Bounded republishing may produce duplicates carrying the same work intent; it never creates another analytical request. A worker may finish before publisher acknowledgment, so a late publisher update cannot overwrite the completed work state.
3. **Claim on receipt.** Validate the envelope against current intent and live owner/source/subject state. Atomically claim eligible work and its exact revision. A duplicate with an active valid claimant does no effects; obsolete/deleted/completed work is a no-op. A live lease prevents a competing coordinator, not mere message-ID equality.
4. **Execute through domain guards.** Revalidate deadline/capacity, reconstruct committed state and perform only the next legal operation. Runtime, not Celery chains/chords or cloud queue ordering, owns specialist routing, parallel joins, mandatory review and finalization. Do not create a Celery task for every specialist or use transport retry as an action retry.
5. **Commit a handoff before normal completion.** Terminal work, committed clarification/import waiting, or a bounded retryable/blocked disposition records its delivery consequence and releases the work claim. Waiting releases execution resources; the accepted matching reply creates an idempotent next wake for the original subject. No worker sleeps while a human answers.
6. **Acknowledge transport delivery.** A normal return acknowledges after its durable handoff. Lost acknowledgment may redeliver, and the next worker reads that same handoff. Abnormal child death/failure can be acknowledged by Celery without a recorded handoff: the still-unfinished Postgres intent is deliberately recoverable by reconciliation. Broker acknowledgment never marks domain success or deletes the only pending-work record.

Use finite backoff and transport retry caps stored with the original WorkIntent. Unknown commits resolve by identity before another mutation. Do not use Celery generic autoretry around execution, unbounded requeue loops, long ETA/countdown messages as durable schedules, or a new work ID to reset an exhausted delivery budget. Exhaustion blocks delivery with a sanitized operator-visible diagnostic; legal same-run recovery still needs remaining policy/configured allowances and current scope. A client reconnect is never a work wake by itself.

## Selected Celery/Redis transport and acknowledgment policy

Use allowlisted task names/queues, JSON accepted content, ignored Celery task results and no result backend. Queue/control status, accounting, outcomes and errors already belong to Postgres; do not add django-celery-results or a second result authority. Use late acknowledgments, prefetch multiplier one, acknowledgment on failure/timeout, and worker-lost rejection disabled; verify these policy choices against the exact pinned build before enablement. The last choice avoids unbounded broker poison-message loops; the database reconciler supplies bounded missing-work recovery even when a child-death message is acknowledged. Validate the exact chosen Celery/Kombu/Redis build behavior before enabling it.

A Redis visibility timeout can redeliver work even while an earlier worker is alive. Set and test it consistently with bounded worker handoffs and shutdown behavior, but do not treat a large value as a correctness mechanism. Claims and domain fencing must tolerate any duplicate. Broker publish/connection retries are finite and do not retry model/sandbox calls. No Celery task ID is assumed to enforce deduplication.

Use distinct Redis logical databases/namespaces for the broker, Channels notifications and graph checkpoints. This is organizational separation, not CPU/memory/failure isolation: the local shared service needs explicit capacity, no uncontrolled eviction and tested outage/full-storage behavior. Data loss is handled by the approved ledger-led reconstruction, subject to checkpoint outage policy. Do not flush the shared Redis service or another feature's keys during recovery. Exact Redis persistence, ACLs and resource/connection settings are implementation gates, not assumed measured properties.

## Ownership, interruption, deletion and uncertainty

Renew the domain coordinator lease independently of an individual blocking provider call and with its own bounded database connection/timeout. A worker heartbeat, Celery liveness flag, queue lease or Redis key cannot renew/replace the domain fence. Loss of lease or irreconcilable time blocks new effects and publication. A replacement worker first acquires/reconciles the current generation; the old one remains fenced even if it later returns.

Expired WorkClaim/worker leases only establish that ownership may be taken over. They do not prove a provider call was unsent or a sandbox retired. Recovery restores canonical results/verdicts/waits, adopts saved validated responses under current guards, reconnects identifiable unresolved work, and only then considers a bounded replacement. A potentially active execution retains its retirement barrier and reserved resources across worker failure and terminal UI errors. Killing/revoking a Celery task or expiring a cloud message is not sandbox retirement proof.

Source/Chat/result/Project revocation commits immediately through the approved authority and fences relevant work. Queue purge/revoke is optional waste reduction, never the authorization boundary. A queued stale envelope is rejected after removal, even if it predates the tombstone. Graceful shutdown stops new claims, records/reconciles the current handoff and drains within a configured bound. Forced shutdown is an uncertain crash, not automatic permission to rerun tools or refund usage.

Queue wait and restart do not extend original hard deadlines. Time outside an explicit committed human-wait period follows the existing conservative active-time policy. Renewing work delivery/leases never renews model/review/wall-time budgets. Admission and dispatch reject unavailable capacity rather than silently funding an infinite pending queue. Exceptions produce interrupted/retryable state only when no terminal publication exists and legal recovery remains; otherwise follow the existing bounded terminal notice policy.

## WebSocket updates and Phase 5 handoff

Workers commit public stage/card/publication/revocation delivery records alongside domain changes. The notification sender wakes Channels with bounded IDs/revisions; sockets re-read current authorized state, replay missed deliveries and chunk only already committed eligible answers. Broker success, notification success and browser acknowledgment are separate. A missed final notification is repaired by durable-watermark reconciliation without model calls or new runs.

Phase 5 integrates worker startup with the same standalone recovery entry point: run_id is checkpoint thread identity, Postgres remains authoritative, nine parent fields and child namespaces are preserved, and a missing/ahead/wrong-schema checkpoint follows the approved rebuild/quarantine/block rules. Phase 4 supplies claimed scope/fence/configuration and a durable disposition; it does not invent a fresh run to load a checkpoint. Exact runtime adapter APIs and graph version/serializer identity are implementation evidence, not inferred from existing source module names.

## Implementation slices and acceptance

| Slice | Required evidence |
| --- | --- |
| W1 work intent/claim contract | Real Postgres uniqueness and races: command+intent atomicity, conflicting replay, publish outcome unknown, worker-before-publisher-ack and concurrent duplicate claims. Source removal/terminal state checks fail closed. |
| W2 selected broker adapter/processes | Use actual local Celery/Redis for transport evidence; scripted/eager runs do not prove broker behavior. Verify duplicate delivery, acknowledged child death, poison tasks, queue loss and broker outage against unfinished durable intents. No eager/scripted-only result is claimed as broker proof. |
| W3 lifecycle/controller integration | Admission, complete import publication, frozen run continuation, wait/reply release and preserved successful siblings. Independent screening/control and execution roles obey shared capacities and deadlines. Generated execution remains isolated. |
| W4 reconciliation/retirement/delivery | Crash before/after each handoff, missed heartbeat, stale owner response, unknown external operation, deletion while queued/running/waiting, safe cleanup, missed Channels wake and interrupted recovery. No duplicate analytical effects or extra review passes. |
| W5 operational handoff | Pinned Linux worker/broker/protocol builds, restart/shutdown/full-storage tests, finite queue/prefetch/lease/visibility/backoff/timeout/resource settings and bounded sanitized diagnostics. Phase 5 then proves worker/checkpoint restore; Phase 6 proves combined real backend flows. |

Public observability includes durable work state, queue age, claimed owner generation, dispatch/recovery attempts, stalled/blocked reason and delivery lag, without questions, uploaded cells, exact prompts/responses or secrets. Metrics distinguish transport attempts from model/sandbox charges. Correlation IDs stay governed by scope/deletion policy. No health check implies live sandbox/provider readiness.

Transport/process choices and consequential contracts are approved. Exact executable settings and measured acceptance remain assigned to implementation. Implement Celery/Redis only; do not build speculative multi-broker fallback. No automatic paid failover or Cloudflare service creation is proposed.
