# Backend integration and failure verification

**Verification design approved and planning closed, 26 November 2026. All new scenario results remain unrun.** See the [closure and remaining owners](../memory.md#backend-integration-planning-closure--26-november-2026). The [integrated acceptance contract](evaluation-observability.md#integrated-acceptance-and-readiness), [PRD showcase acceptance](../PRD.md#showcase-acceptance), and approved [storage](database-storage.md), [API/WebSocket](backend-api.md), [worker](background-workers.md) and [checkpoint](worker-checkpoints.md) guides own behavior. This guide defines combined application evidence, not new runtime policy or a substitute agent evaluation suite.

## Verification scope and layers

Use a deterministic integration harness and independent scenario/oracle manifest, with three explicitly separated layers:

| Layer | Real components and permitted claims |
| --- | --- |
| L1 focused contract checks | Strict DTOs, service/adapter operations, real Postgres transaction/constraint tests where applicable, and Channels consumer tests. Useful focused regression evidence; in-process clients/communicators do not prove browser Origin/cookie/proxy behavior, process restart or broker delivery. |
| L2 combined local backend | Actual isolated Postgres, persistent files, Redis JSON/search, Celery control/execution/maintenance, ASGI/Channels and a real browser/native protocol client through the same-origin ingress. Model and sandbox transports are trusted deterministic scripts at the approved external adapter boundaries. Exercises actual orchestration, ledger, publication/recovery and application delivery. This proves the declared backend integration behavior, not real inference quality or OS sandbox enforcement. |
| L3 integrated live capability | The same path using admitted provider/sandbox/validator capabilities and compatible manifests, only after their prerequisites, finite spend/resource forecast and separate live authorization. Reuse the existing independent fixtures/evaluation gates. A scripted pass never enables an unproven execution capability or claims an agent milestone. |

Use Django's existing test tools/TransactionTestCase and Channels communicators for focused checks, plus a small process/controller harness for L2. Use the Python Playwright library as a development-only real-browser driver; no completed React product UI is required. A test-only same-origin protocol page can exercise fetch, cookies, WebSocket Upgrade/frames and reopen/reconnect. It is not a replacement frontend, a user-facing debugging screen or another product interface. Browser binaries/dependencies are pinned by the owning implementation task, not installed during planning. Keep the agent's existing test environment separate from the backend's.

Prefer this to an all-mocked end-to-end suite or waiting for the finished React frontend. Mocks cannot prove transaction/process/network behavior; waiting for UI would postpone backend boundary failures. Avoid a new workflow engine, model judge, custom broker or redundant mirror of every schema field. Reuse component checks and add scenarios only where combined boundaries introduce risk.

## Current evidence and execution prerequisites

Backend inspection found its Django dependency scaffold and no backend test/Compose harness in the targeted file discovery. Existing agent test filenames include crash/dispatch/format themes, but inspected portions of `test_crash_boundaries.py` and `test_dispatch_collection.py` construct simple contracts or use a trivial assertion without process/broker/crash behavior. Those inspected cases are not restart or adversarial-flow evidence; this is not an audit of every test or a claim the full suite passed/failed. The separate Redis projection helper's TTL/state/saver conformance remains a prerequisite recorded in [checkpoint integration](worker-checkpoints.md#existing-decisions-and-observed-implementation-boundary).

Before L2 execution, require compatible implemented component interfaces, real schema migrations/constraints, selected Celery/Channels/RedisSaver wiring, an exact dependency/container/browser manifest, finite operational limits and trusted scripted transport implementations. Missing prerequisites produce blocked/not_run evidence rather than silently substituting SQLite, MemorySaver, eager Celery, an in-memory channel layer or invented success responses. Scripted transports may only simulate external results/failures; they cannot bypass the real admission, accounting, validation, retirement protocol, storage or publication guards being tested.

Use an isolated, explicitly named test Compose project with fresh synthetic Project/run identities, distinct database/Redis namespaces, dedicated file volumes and loopback ports. No operator development data, shared live queue, stored credentials or unrelated container/process is a test target. The harness records resolved targets/labels and rejects any kill, disconnect, quota or cleanup action outside its test inventory. Do not mount infrastructure control sockets into the application, workers or generated-execution environment. Fault control is a host-side test facility, absent from production HTTP/WS routes and normal configuration.

Preparing this design authorizes no fault run or infrastructure start. Actual destructive fault injection stays inside the separately authorized isolated execution batch and cannot turn a testing tool into a production Stop API. Live transports stay disabled and credentials absent in L2; zero paid-spend caps remain effective. Network controls must prove unexpected external dispatch fails before claiming the suite was offline/scripted.

## Fixtures, oracles and event controls

Each scenario records a stable ID, authoritative contract/version, layer, capabilities/prerequisites, configuration/seed/fixture digests, exact request identities, fault/barrier schedule, expected required/forbidden events, ledger/artifact/public-state assertions and evidence references. Independent oracles are checked-in trusted fixture expectations or separately reviewed deterministic calculations, not values obtained by asking the agent, copying its displayed answer or running the production analytical helper as the oracle.

Use a small synthetic A/B fixture family. Example: A has users u1/u2/u3; B has purchase events u1=5, u1=5, u2=10 plus a nonpurchase u3 event. Independent expectations include distinct purchasers 2, eligible users 3 and purchase total 20. A naive joined purchase-row count of 3 must not become the distinct-user numerator. Preserve numerator/denominator as exact typed values; display rounding is separately checked against the approved renderer. Add independent ingestion/canonical fixtures for the already approved null/empty/leading-zero/decimal/temporal/format rules rather than reauthoring or expanding that policy here.

For deletion survivors, create a genuinely A-only run with A-only source-bearing context, preferably in a fresh Chat, alongside an A+B-dependent run. Merely writing SQL that reads A while the supplied drafting/history packet depends on B is not an independent survivor. Include a source-free analytical/help response as a separate provenance case. Import profiles, executed SQL/Python, typed evidence/locators, draft/review input hashes and served artifact bytes must agree with their canonical metadata.

Use explicit bounded barriers around existing durable boundaries, not timing guesses or arbitrary sleeps. A barrier identifies transition/work/run/attempt and emits a content-free receipt; the controller releases or crashes the owned process at that receipt. Policy-clock fixtures can shorten deterministic timing checks through the approved clock interface, but separate real process/lease/deadline tests are still required. A smaller test limit does not prove the actual PRD 50 MiB raw cap; include the declared production-boundary case with generated streaming fixture bytes.

Entry rejection/wait/unavailable never fabricates an admitted run. |

| B04 Direct and correction controls | Compatible prior/profile evidence and source-free Direct keep their labels and no execution/Reviewer calls. | B07 deletion and dependency closure | Remove B while A+B work is queued, running or waiting; prevent further effects/publication and show source-unavailable. | B08 duplicates and unknown commits | Lost HTTP/socket receipt, repeated idempotency key, changed content under a key, concurrent commands/replies, duplicate Celery deliveries and broker publish/worker completion acknowledgment loss produce the same canonical operation/receipt/publication or explicit conflict. | B09 worker/checkpoint restart | Kill the owned process at registered durable barriers and start a fresh worker. ## Fault/race boundary packet

The manifest maps each injected fault to its applicable Bxx scenario and component acceptance gate. Required high-risk boundaries include:

| Boundary | Crash/race evidence |
| --- | --- |
| Command receipt/WorkIntent commit → broker publish | Kill before callback/publish; intent survives and eventually dispatches once under guards. Duplicate publish/unknown broker acknowledgment cannot create a second domain request. |
| Worker claim → dispatch reservation → external send | Two recipients contend; stale generation cannot send/adopt/publish. Crash after reserved-but-unknown send preserves physical exposure and original ownership/retirement requirements. |
| Execution complete → validation/transfer → metadata commit | Uncommitted candidate never becomes evidence. Lost acknowledgment after commit resolves the same artifact/outcome. Corrupt/missing committed bytes fail integrity rather than recompute under an old ID. |
| Domain commit → checkpoint write → adopted descriptor ack | Kill at all three gaps and test partial root/child/index state. Restore follows Postgres, not raw Redis latest; existing valid work and charges remain. |
| Review pass/verdict → terminal publication | A restart consumes neither a free extra review nor a second publication; deadline/source/candidate checks still gate publication. |
| Question/wait commit → card delivery → accepted reply claim | Lost delivery/reply acknowledgment, competing reply and user reopening preserve the same question, accepted reply and original basis. |
| Source/owner tombstone versus dispatch/adoption/publication/read/cleanup | Deliberately run both linearization orders on separate DB connections and worker processes. Immediate revocation holds while physical cleanup may remain pending; new refs cannot race an object marked deleting. |
| Publication/delivery commit → notification/chunk/ack | Drop the final wake and disconnect before/after chunks; replay the same identity or revoked disposition. No content is pulled directly from an untrusted channel message. |

Record barrier arrival and fault action so a passing test proves the intended path was exercised. A test that misses its barrier is failed/blocked harness evidence, not a pass of the target condition. Automatic reruns cannot erase the original failure. Keep regression seeds and minimized reproductions; broaden testing only when a change/failure/unresolved risk justifies it.

## Assertions, reports and acceptance decisions

Collect three independent observations for combined scenarios: authoritative ledger/constraint/call-accounting state; persisted artifact/checkpoint/retirement inventory; and HTTP/browser/WebSocket-visible outcomes. Required/forbidden external adapter calls are counted by stable physical identity, not just task-function invocation or trace prose. Browser display alone cannot prove no duplicate spending, and a ledger success alone cannot prove user delivery or revoked bytes are inaccessible.

Reuse the approved gate statuses proposed/not_run/blocked/passed/failed, with applicability reasons for any excluded capability. Each assertion maps to contract version, component owner, layer, fixture/configuration/build/commit plus dirty-patch digest and evidence reference. Reports preserve missing prerequisites, crash point, original attempt and rerun outcomes. Separate test-harness/infrastructure blockage from a demonstrated product violation; neither is a pass. A changed manifest invalidates old evidence unless an explicit applicability review and required rerun establish otherwise.

Every applicable authority/identity/access/isolation/privacy/source invalidation/publication/retirement/budget invariant is pass/fail. Any observed violation fails that configuration regardless of answer quality or the number of happy-path passes. Do not report “backend verified” from a favorable average while required scenarios are blocked or unrun. Model semantic quality and real sandbox enforcement remain separate existing gates; scripted correctness labels cannot replace them.

Produce a local structured run manifest/report plus a concise human-readable report linking gate IDs and sanitized evidence. Keep permitted synthetic payload/artifact evidence private to the test run and under deletion policy; publish only the approved allowlisted summary. Do not dump fixture cells, checkpoints, prompts, raw model responses or credentials into hosted logs, screenshots/traces or Floorplan. Trace/video capture is explicitly scoped to synthetic data and redacted; evidence retention is deliberate, not an indefinite content archive.

Declare the verified scope explicitly: focused contracts, combined backend transport/recovery with scripted external transports, and/or admitted live end-to-end capabilities. Record frontend acceptance as pending until Phase 7 proves the actual React workflows. No single success label silently combines these scopes. Report all attempted denominators and failure/timeout/rejection outcomes; observed latencies/resource use are measurements, not new promised service limits. This phase creates no separate model-quality comparison or statistical sample count beyond the existing approved evaluation manifest.

## Execution preflight and cost/resource boundaries

Freeze fixture/oracle/configuration/build identities, finite schedule/repetitions, fault targets, test volume/database/namespace ownership and external transport mode before an authorized batch. Confirm unexpected provider/sandbox/network routes fail closed in L2, and make cleanup dry-run/inventory results reviewable before destructive actions. Tear down only resources proven to belong to that test batch; retain bounded non-content failure diagnostics when cleanup is blocked. Do not mutate another local worker or the user's retained data merely to provoke a fault.

For L3, reuse the approved full cost preflight: every model role/repair/retry/judge plus sandbox/storage/validator usage, cache assumptions, repetitions, unknown exposure and hard caps. Distinguish zero external billing in a proven scripted run from local CPU/disk usage or unknown account billing. Compare forecast with actual billed scope before reporting live results. No live invocation, deployment or cost-bearing service is authorized by approval of this design.

## Implementation/verification handoff

1. **V1 manifest/oracles and focused harness:** author/review synthetic fixtures, required/forbidden events, barriers and strict report schemas; reuse meaningful component tests. Confirm existing crash-labeled assertions actually exercise the claimed behavior before counting them.
2. **V2 isolated real backend stack:** implement trusted scripted adapters and actual Postgres/Redis/Celery/ASGI/browser fixture wiring, capability preflight and owned teardown; no product policy bypass or public fault endpoint.
3. **V3 combined normal/control flows:** execute B01–B06 and typed evidence/lineage checks once prerequisites pass; preserve result scope and all failures.
4. **V4 concurrency/crash/revocation:** execute applicable B07–B13 and the fault packet with actual processes, independent transactions and bounded barriers. Fix authorized defects under their owning specs; rerun affected scenarios, not an automatic full speculative suite.
5. **V5 evidence/readiness handoff:** reconcile scope/gates, actual costs/resources and privacy/cleanup; link remaining live and frontend owners. L3 waits for independent execution admission/authorization and applicable agent gates. Phase 7 consumes the stable API and backend verified-scope report rather than inferring it from design approval.

The exact test file/module names and executable commands are implementation choices to define against the built environment; no nonexistent test command is presented as passing. Suggested placement is backend-owned integration fixtures/controller/scenarios and test-only protocol clients, with durable acceptance contracts here and outcome records in the existing gate/evidence system. CI remains Phase 8; this is a local verification workflow first.
