## Execution boundary

Use a deterministic ingestion pipeline with trusted importer code for parsing, header detection, type inference, validation, and profiling. Resolve ambiguous import settings through the user confirmation preview. Analysis by the agent starts once the Dataset is ready. Use separate sandbox sessions for ingestion and analysis. Ingestion receives a staged upload and confirmed settings, and produces the prepared database, catalog, and warnings. Analysis receives authorized prepared snapshots and required prior results, and produces evidence, charts, and execution errors. The worker controls file transfer and saves reusable outputs to persistent storage before releasing a session. Inspect uploads for the preview in an isolated session and release that session while awaiting user confirmation. Use one sandbox per active analysis run and reuse its staged files across actions. Give each action a separate execution context and output directory. Persist reusable outputs after each action. Release the sandbox on clarification, completion, or timeout. Recovery creates a fresh session from saved files and checkpointed state. Use one DuckDB connection per SQL action, reuse it for that action's queries, schema inspection, and query corrections, and close it when the action finishes or fails. Concurrent SQL actions use separate connections. Trusted runtime code attaches the authorized prepared Dataset files read-only under controlled aliases and supplies those aliases and table schemas to the SQL Specialist. The runtime owns attachment setup and file path resolution. Each model-generated SQL execution call contains one analytical query, supporting CTEs, joins, aggregations, and window functions. Before execution, the runtime validates the parsed query against permitted tables and functions. Reject commands that modify data, attach files, load extensions, or change settings. Trusted code saves the complete query result as a typed Parquet artifact and returns a bounded preview, row count, column types, and evidence reference to the agent. Python actions can load the saved artifact when they need the full result. If a result exceeds the configured storage limit, report the limit so the specialist can narrow the query. Preview sizes and result limits remain open for evaluation. For each saved query result, record an evidence UUID, run/task/action identifiers and attempt number, executed SQL and parameter values, Dataset snapshots and tables actually referenced, artifact reference, row count, schema, and integrity checksum. Use this provenance to support review, reproduction, and source-removal invalidation. Exact field types and source-reference extraction remain open. The SQL parser, function policy, and sandbox enforcement remain open. Disable outbound internet access in ingestion and analysis sessions. The worker makes model calls under the approved provider policy outside the sandbox and transfers authorized files through the sandbox service. Preinstall required libraries in the sandbox image and keep model credentials outside the sandbox. Make staged analysis inputs read-only. Actions write to their own temporary and output directories. The worker retrieves only declared outputs after validating their paths, types, and sizes. Give each sandbox only authorized inputs and required runtime files. Verify filesystem enforcement with the chosen provider. Enforce finite limits for sandbox CPU, memory, execution time, temporary disk, expanded input size, and output size in addition to the 50 MiB raw upload cap. If a limit is exceeded, return an explicit failure identifying that limit. Any reduction of data or sampling requires a deliberate decision because it can change the answer. Choose numerical limits through ingestion and analysis benchmarks. Execute each SQL action in its own subprocess and DuckDB connection inside the run sandbox. Each Python action owns an execution context and process tree whose serial code calls use fresh interpreter children and fresh scratch/output areas; only published artifacts carry results between calls. Keep action outputs isolated. On an action timeout, terminate its process tree. If the whole sandbox fails, recover unresolved actions under the checkpoint recovery policy. Python actions pass saved artifacts between steps. Pin the sandbox template and Python dependencies. Use the same DuckDB version for ingestion and analysis, and record the environment version with prepared datasets and evidence. Provider support and enforcement of the execution boundaries remain to be verified. Environment identifiers and upgrade compatibility rules remain open.

### Python execution target

Python rounds 3A/3B refine execution within the shared run sandbox: fresh interpreter and scratch/output area per code call, explicit per-call evidence inputs, and separately published numerical work before chart rendering. The approved OS target uses per-call bubblewrap, protected exit supervision, bounded controller-owned writable storage, cgroup-v2 resource/termination controls and isolated output validation. The detailed contract is in [Python Specialist](python-specialist.md). This is a target pending live feasibility verification; do not execute generated Python unless the required profile can be enforced. SQL's persistent action runner/connection is unchanged.

### E2B assessment

E2B assessment (12 November 2026). E2B Hobby was provisionally selected on 13 November 2026. Before integration, verify filesystem enforcement, process-tree termination, recovery after worker disconnection, and account resource availability. Its documentation supports outbound network blocking while retaining SDK file/command access, background commands with process handles, configurable users and working directories, and prebuilt templates. A command handle can be killed, but full process-tree termination still needs verification. Read-only inputs and per-action filesystem boundaries require a hardened template and validation. Separate output directories alone do not enforce action isolation. Sandbox CPU and memory are shared by actions, so per-action limits require additional enforcement. Use reconnect-first recovery after a worker disconnects. Save the sandbox ID, command ID, action ID, and attempt number before waiting for completion. Reconnect to an identifiable running command and collect its outcome. If its execution state cannot be recovered, retire the old sandbox before recreating the session and replaying unresolved actions under the agreed at-least-once policy. Reuse persisted successful outcomes. The runner writes a completion record with action and attempt IDs, status, output references, and checksums. Recovery validates the record and outputs before saving the outcome in outcomes. If validation fails, the action remains unresolved. The completion record schema, command launch bookkeeping, and handling an unreachable sandbox remain to be specified and tested.

Published E2B Hobby pricing has a zero monthly base, 10 concurrent sandboxes, a one-hour continuous session limit, and a one-time $100 credit. A sample configuration of 2 vCPUs and 4 GiB RAM costs $0.000046 per running second ($0.1656 per hour). At this rate, 300 analysis runs taking two minutes each cost $1.656, or five minutes each cost $4.14. Add ingestion, inspection, file-transfer time, and time waiting for model calls while the sandbox runs. These are forecasts before credits and taxes. Confirm account resource availability because the billing guide and pricing page differ on default resources and customization. No live E2B session was created for this assessment.

## Environment, admission and lifecycle contract

Prepared 19 November 2026; **design approved 20 November 2026**. This section resolves the earlier open ownership/configuration details while preserving approved SQL/Python controls. Approval does not establish provider feasibility or authorize execution. The following ceilings are accepted intersecting development candidates, subject to measurement. Existing stricter role/action/run ceilings win. See the [phase closure](../memory.md#final-agent-architecture-phase-closure--20-november-2026).

### Environment identity and compatibility

Controller-owned EnvironmentManifest records manifest/schema version, immutable image digest and provider template revision, OS/kernel/architecture, Python and exact package/build/lockfile hashes, DuckDB and Arrow builds, SQL parser/policy version, importer/profile/validator versions, locale/timezone rules and enforced isolation/resource profile. Record creation time and provider identity without credentials. The manifest identifies observed effective controls separately from requested settings and links to the enforcement gate results for that exact build.

Every prepared snapshot, profile and execution result references its producer manifest. Initial compatibility is exact equality of the preparation/analysis DuckDB build and supported schema/codec versions; consumer libraries must pass typed round-trip fixtures. A changed image is not automatically compatible because it contains the same package names. The runtime maintains an explicit supported producer/consumer tuple register with fixture evidence. Unknown tuples block admission. Immutable old snapshots are never upgraded in place: an explicit rebuild from retained source/settings creates new snapshot provenance and revalidates dependent access. Provider/template aliases alone are insufficient build identity.

### Resource admission and candidate development envelope

| Resource | Candidate ceiling and accounting |
| --- | --- |
| Session | 2 vCPUs, 4 GiB total RAM, 4 GiB total controlled filesystem allocation including input copies, scratch, quarantine, output and validator copies. Reserve controller/validator overhead before admitting work. |
| Executing action | Ingestion, SQL or Python: 1 vCPU and 2 GiB process-tree RAM within the session; DuckDB's internal memory limit is at most 1 GiB, with spill inside charged scratch. OS limits remain mandatory. |
| Initial development scheduling | One executing analysis action at a time. This intentionally narrower profile does not remove the approved two-action branch capability. A later two-action profile requires enough aggregate resources for both actions plus protected controller/validator overhead and concurrent-isolation proof. |
| Preparation/inspection | One ingestion action/session, at most 1 GiB expanded logical input including archive members and parser materialization, within session RAM/disk limits; 120 seconds preparation and 30 seconds inspection wall time. Uncertain or unknown expansion cannot bypass the cap. |
| Writable action scratch | 1 GiB aggregate across the action process tree. Unpublished artifacts and temporary spill count here; failed/retried work is not free capacity until retirement/cleanup. |
| Published action output | 128 MiB total across declared artifacts, at most 16 files, each counted before transfer; transfer/validation copies also consume session/controller capacity. Complete results only, never silent truncation. |
| Execution | SQL query: at most the approved 30 seconds. Python code call: at most 60 seconds, intersected with its existing stricter action/call limits. Neither resets enclosing action time. |
| Session lifetime | At most 300 seconds from creation, including model/transfer/validation idle time. Begin no work that cannot fit with retirement/collection reserves. A run may use a fresh session after prior work is collected/retired, under unchanged run counters/deadlines. |
| Import diagnostics | At most 20 source locations and 2 KiB text per item; exact failure count only for fully validated scope, otherwise explicit incomplete coverage. Diagnostics do not extend parsing deadlines. |

The controller reserves resources durably before dispatch, including host-side quarantine/storage and model-independent waiting/retirement exposure. A larger file can fail these development limits even while satisfying the separate 50 MiB Project raw-upload cap. That is an explicit limit failure, not permission to sample. Retained uploads and completed outputs follow user deletion policy, not session TTL. Project/operator admission additionally bounds concurrent sessions and retained bytes; initial local profile permits one active session and 2 GiB persistent prepared/evidence artifacts, with replacement requiring room for both versions. Reaching that storage ceiling blocks new publication and keeps existing results accessible.

Limits are configured and enforced by the controller/OS, not model instructions. A resource error records limit kind, configured ceiling, known observed usage, execution/validation coverage and retained usable evidence. Unknown usage stays unknown. Any stricter approved limit or remaining reserve prevents dispatch sooner. Exact enforcement, parser fidelity and representative capacity/performance remain measured gates, not more architectural rounds.

### Transfer, publication and cleanup

Ingestion inspection and preparation use sessions separate from analysis. Waiting for import confirmation closes the inspection session; later preparation reconstructs only from immutable upload/settings. SQL reads authorized ready snapshots; Python receives only its explicit authorized evidence artifacts. No upload, provider-mounted bucket or saved workspace becomes an alternative runtime authority.

The trusted controller owns staging paths and file transfer. Treat every sandbox output as untrusted: copy declared bounded regular files into inaccessible quarantine, reject path traversal/symlinks/devices/unexpected types, verify size and checksum, then perform isolated format/schema/content validation. The output validator cannot access secrets or unrelated artifacts. Sandbox-provided checksums are checked against controller-read bytes. Persist a validated candidate and verify the durable copy before attempting the existing guarded ledger publication transaction. Source deletion, ownership/attempt generation, artifact availability and deadlines are rechecked there; successful transfer alone cannot mark a Dataset ready or expose evidence.

The ingestion [preparation lifecycle](data-ingestion.md#preparation-lifecycle-replacement-and-cleanup) owns the atomic snapshot/catalog/profile ready transition. Execution uses the approved SQL/Python operation publication/retirement contracts. On lost acknowledgment, read the canonical committed result. A crash before publication leaves quarantined candidates ineligible. Never replay uncertain execution merely because the transfer or command client timed out.

Persist provider sandbox/command ID, incarnation, action/operation/attempt and ownership generation before waiting. Reconcile live completion and trusted manifests; otherwise fence publication and establish whole-process-tree retirement before replacement or cleanup. Pause, expiry notification or an unreachable handle is not retirement proof. An unreachable unretired incarnation retains its capacity reservation and produces a recoverable infrastructure stop. Do not overcommit around it. Confirmed retirement permits removal of only that incarnation's unreferenced temporary files; tombstones/access denial precede physical source cleanup.

### Enablement and provider alternatives

Required proof includes read-only authorized inputs, denied outbound traffic with controller transfer preserved, per-action filesystem separation, Python's bubblewrap/cgroup-v2/protected supervisor profile, SQL function/relation lockdown, bounded child/fork/memory/disk/output behavior, isolated output validation and retirement across worker disconnect/crash. Reconnect and lost-ack fixtures must preserve operation identity and prevent duplicate publication. Generated execution remains disabled when a required control is unsupported or untested.

E2B remains provisional; neither its historical credit nor Cloudflare's AI allowance establishes free sandbox execution. The [provider configuration proposal](role-prompts-models.md#provider-configurations) keeps Cloudflare inference separate from Sandboxes, R2 and D1. No infrastructure substitution is approved here. Exact image/package identities are build-time pins; a successful build alone does not pass live enforcement gates.
