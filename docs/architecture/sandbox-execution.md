## Execution boundary

Use a deterministic ingestion pipeline with trusted importer code for parsing, header detection, type inference, validation, and profiling. Resolve ambiguous import settings through the user confirmation preview. Analysis by the agent starts once the Dataset is ready. Use separate sandbox sessions for ingestion and analysis. Ingestion receives a staged upload and confirmed settings, and produces the prepared database, catalog, and warnings. Analysis receives authorized prepared snapshots and required prior results, and produces evidence, charts, and execution errors. The worker controls file transfer and saves reusable outputs to persistent storage before releasing a session. Inspect uploads for the preview in an isolated session and release that session while awaiting user confirmation. Use one sandbox per active analysis run and reuse its staged files across actions. Give each action a separate execution context and output directory. Persist reusable outputs after each action. Release the sandbox on clarification, completion, or timeout. Recovery creates a fresh session from saved files and checkpointed state. Use one DuckDB connection per SQL action, reuse it for that action's queries, schema inspection, and query corrections, and close it when the action finishes or fails. Concurrent SQL actions use separate connections. Trusted runtime code attaches the authorized prepared Dataset files read-only under controlled aliases and supplies those aliases and table schemas to the SQL Specialist. The runtime owns attachment setup and file path resolution. Each model-generated SQL execution call contains one analytical query, supporting CTEs, joins, aggregations, and window functions. Before execution, the runtime validates the parsed query against permitted tables and functions. Reject commands that modify data, attach files, load extensions, or change settings. Trusted code saves the complete query result as a typed Parquet artifact and returns a bounded preview, row count, column types, and evidence reference to the agent. Python actions can load the saved artifact when they need the full result. If a result exceeds the configured storage limit, report the limit so the specialist can narrow the query. Preview sizes and result limits remain open for evaluation. For each saved query result, record an evidence UUID, run/task/action identifiers and attempt number, executed SQL and parameter values, Dataset snapshots and tables actually referenced, artifact reference, row count, schema, and integrity checksum. Use this provenance to support review, reproduction, and source-removal invalidation. Exact field types and source-reference extraction remain open. The SQL parser, function policy, and sandbox enforcement remain open. Disable outbound internet access in ingestion and analysis sessions. The worker makes OpenRouter calls outside the sandbox and transfers authorized files through the sandbox service. Preinstall required libraries in the sandbox image and keep model credentials outside the sandbox. Make staged analysis inputs read-only. Actions write to their own temporary and output directories. The worker retrieves only declared outputs after validating their paths, types, and sizes. Give each sandbox only authorized inputs and required runtime files. Verify filesystem enforcement with the chosen provider. Enforce finite limits for sandbox CPU, memory, execution time, temporary disk, expanded input size, and output size in addition to the 50 MiB raw upload cap. If a limit is exceeded, return an explicit failure identifying that limit. Any reduction of data or sampling requires a deliberate decision because it can change the answer. Choose numerical limits through ingestion and analysis benchmarks. Execute each SQL or Python action in its own subprocess inside the run sandbox, with its own connection or interpreter and output directory. On an action timeout, terminate its process tree. If the whole sandbox fails, recover unresolved actions under the checkpoint recovery policy. Python actions pass saved artifacts between steps. Pin the sandbox template and Python dependencies. Use the same DuckDB version for ingestion and analysis, and record the environment version with prepared datasets and evidence. Provider support and enforcement of the execution boundaries remain to be verified. Environment identifiers and upgrade compatibility rules remain open.

### E2B assessment

E2B assessment (12 November 2026). E2B Hobby was provisionally selected on 13 November 2026. Before integration, verify filesystem enforcement, process-tree termination, recovery after worker disconnection, and account resource availability. Its documentation supports outbound network blocking while retaining SDK file/command access, background commands with process handles, configurable users and working directories, and prebuilt templates. A command handle can be killed, but full process-tree termination still needs verification. Read-only inputs and per-action filesystem boundaries require a hardened template and validation. Separate output directories alone do not enforce action isolation. Sandbox CPU and memory are shared by actions, so per-action limits require additional enforcement. Use reconnect-first recovery after a worker disconnects. Save the sandbox ID, command ID, action ID, and attempt number before waiting for completion. Reconnect to an identifiable running command and collect its outcome. If its execution state cannot be recovered, retire the old sandbox before recreating the session and replaying unresolved actions under the agreed at-least-once policy. Reuse persisted successful outcomes. The runner writes a completion record with action and attempt IDs, status, output references, and checksums. Recovery validates the record and outputs before saving the outcome in outcomes. If validation fails, the action remains unresolved. The completion record schema, command launch bookkeeping, and handling an unreachable sandbox remain to be specified and tested.

Published E2B Hobby pricing has a zero monthly base, 10 concurrent sandboxes, a one-hour continuous session limit, and a one-time $100 credit. A sample configuration of 2 vCPUs and 4 GiB RAM costs $0.000046 per running second ($0.1656 per hour). At this rate, 300 analysis runs taking two minutes each cost $1.656, or five minutes each cost $4.14. Add ingestion, inspection, file-transfer time, and time waiting for model calls while the sandbox runs. These are forecasts before credits and taxes. Confirm account resource availability because the billing guide and pricing page differ on default resources and customization. No live E2B session was created for this assessment.
