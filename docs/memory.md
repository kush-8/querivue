Explain in the preview that saved formula results are used and can be stale. The formula importer library and multi-table detection rules remain open. Recovery can verify the saved file and finish publication or rebuild it. Associate each ingestion attempt with the confirmed import settings and allow only the current attempt to publish. Repeated delivery after successful publication returns the existing result. A late attempt cannot overwrite or invalidate newer preparation. Delete temporary files belonging to failed or superseded ingestion attempts once those attempts are confirmed inactive. Exact attempt identity, detailed publication mechanics, inactive-attempt detection, and cleanup timing remain open. If a selected type conversion fails, block import of the affected table and show the failure count and sample source locations. The user can choose a compatible type or correct the source. | Local file storage | Store uploads, prepared datasets, and artifacts on a persistent Docker volume shared by the Django API and worker. Postgres stores their references and metadata. |
| Hosted deployment direction | After the local build, the intended hosted setup is a Vercel frontend and Supabase for Django PostgreSQL. Render and DigitalOcean are candidates for the Django API and worker. The backend host and file storage choice are open. |
| Build sequence | Finish design first. Agreed phase order is standalone agent and CLI, database and storage, backend APIs, background workers, Redis checkpoints, backend integration, React, then GitHub Actions CI. The product cohort walkthrough and exact metric are deferred. |
| Agent milestones | Build grounded SQL first, then routing and follow-ups, Python and charts, analysis verification, full input coverage, and reproducible evaluation. The PRD defines the completion check for each milestone. |
| Project model | A user creates a Project and adds Datasets to it. A Project can contain multiple Datasets. Each Chat belongs to exactly one Project. This replaces the earlier plan to bind a chat to one dataset. |
| Dataset editing | Users can add, remove, and replace Datasets after creating a Project. Each upload is a fixed snapshot. A replacement creates a new Dataset ID, even if the filename is unchanged. An analysis run records its eligible Dataset IDs at submission and a retry never substitutes newer uploads. |
| Dataset scope | A question can use any ready Dataset in its Project by default. Users can name specific sources in their question. Querivue asks for clarification when the choice of source or period could materially change the answer. |
| Upload quota | Cap combined uploads at 50 MiB per Project. Measure the sum of uploaded file sizes across its Datasets. The cap is based on bytes. |
| Dataset replacement | Prepare a replacement before removing the original Dataset. A failed replacement leaves the original and its results available. A successful replacement uses the new Dataset ID and applies the agreed source removal behavior to the original. Add the corrected file separately to keep both versions. |
| Source removal | Removing a Dataset stops queued, running, or clarification-waiting analyses whose recorded scope includes it, even before they read it. Show a source-unavailable notice and let the user submit again. For completed runs, clear only answers, evidence, and artifacts that actually used the removed source. Unrelated turns remain available. |
| Inputs and scope | Accept CSV, TSV, Excel `.xlsx`, SQLite `.sqlite` or `.db`, JSON `.json`, JSON Lines `.jsonl`, and Parquet `.parquet` for exploratory analysis. TSV uses the delimited-file importer with a tab separator. SQLite imports selected tables into a prepared Dataset inside the sandbox. Use SQL and Python for analysis and visualization. Ask a focused follow-up when an ambiguous metric or join could materially change the answer. |
| JSON and Parquet imports | JSON uses a top-level array of flat records. JSON Lines uses one flat record per line. Each record becomes a row. Parquet imports preserve supported stored column types. Each of these formats produces one table per Dataset. |
| Answer contract | Quantitative claims link to inspectable evidence. Show the answer and supporting numbers first, with executed SQL or Python available on demand. A chart is required when the user asks for one. If it fails, return supported findings and label the result as partial. |
| Demo data boundary | Use synthetic or non-sensitive data in the demo. Document sandbox processing and the limited data sent to the model. Keep full files out of model requests and uploaded content out of hosted traces. |
| Retention | Projects, Datasets, Chats, and saved content remain until user deletion, including removal of content that depends on a deleted Dataset. This supersedes the earlier 24-hour retention window. Temporary execution state can have its own cleanup schedule. |
| Application architecture | Django owns persisted Projects, Datasets, Chats, runs, and results, and exposes them through an API. Background workers use the agent package for ingestion and analysis, including after the browser closes. React with TypeScript supports the complete upload, chat, progress, and results workflow. Detailed execution inspection lives in LangSmith. |
| Agent architecture | Multiple specialists, with LangGraph orchestration, LangChain tools and model integrations, and LangSmith observability and evaluation. Use managed sandbox execution for generated SQL and Python. |
| Specialist state and contracts | Each specialist has its own state. The supervisor supplies the inputs needed for its delegated task and receives its result. Define each specialist's state, input and result schemas, and mapping from supervisor state during that specialist's design discussion. The previously illustrated structured task payload remains a proposal; its fields are not approved. |
| Agent inference and evaluation cost | Use OpenRouter for inference across all model-powered agent components, including the supervisor, specialists, and reviewer. Choose model configurations by role after evaluating candidates. Before running the full evaluation suite, forecast its cost using the planned cases, repetitions, expected token usage by role, and provider rates, with cache assumptions stated explicitly. After the run, report actual billed model usage and costs, including cached tokens and retries where applicable. Compare forecast with actual spend and report any separately billed evaluation costs, such as sandbox usage or external judges, within the same stated scope. |
| Supervisor evaluation and observability | Evaluate both answer correctness and agent behavior. Use versioned fixtures with expected calculations and evidence, and check required and forbidden trajectory events for routing, evidence reuse, clarification, prerequisite ordering, retries, and review. Treat safety and recovery invariants as pass/fail gates. Compare the single-agent baseline and specialist configurations on shared fixtures for correctness, completion, active latency, tool calls, retries, and cost. Tune on development cases and use held-out cases for the final comparison. Trace decisions, task and action dispatch, attempts, checkpoint resumes, reviews, and final outcomes. Correlate events with run, task, and action IDs and attempt numbers where applicable. Record concise decision labels, durations, outcomes, and stop reasons. Keep uploaded rows and raw results out of hosted traces. Publish a repeatable CLI evaluation and a report with configuration comparisons and annotated failure traces. Exact event fields, fixtures, and thresholds belong in the observability and evaluation specs. |
| Supervisor limit selection | Choose the final supervisor execution limits from reproducible evaluation results, comparing answer quality, task completion, latency, cost, and recovery behavior. The suggested values are evaluation candidates only: 12 supervisor decisions per run, 3 concurrent specialist tasks, 1 retry of an unchanged task for transient failures, 2 consecutive action rounds without progress, and 5 minutes of active execution excluding clarification waits. These numerical values remain candidates for evaluation. Evaluation runs must still use explicit finite limits. The separately agreed maximum of two review passes remains confirmed. |
| Supervisor failure handling and stopping | After a specialist task fails, the supervisor inspects the failure and may retry, change approach, or continue with available evidence within runtime-enforced limits. When further progress is impossible, return a useful supported partial answer where possible and explicitly identify what remains unanswered. Repeated actions without new evidence must stop with an explanation instead of continuing until timeout. Progress means obtaining usable new evidence, resolving an ambiguity, or completing a requested deliverable. A valid empty result counts when it answers a question about whether matching records exist. Repeating work that adds nothing does not reset the no-progress count. Exact budgets, retry limits, and the no-progress stopping threshold remain open for evaluation. Fresh partial analyses remain subject to the agreed Answer Specialist and Reviewer workflow and two-review limit. Reserve part of the run budget for drafting, review, and finalization. Before dispatching further analysis, enforce that reserve. When analysis reaches the reserve, hand off a useful supported partial answer if possible. If the evidence cannot support a useful answer, explain what is missing. Choose the reserve size through evaluation. Immediately before publishing any answer, check the run for source invalidation under the agreed source-removal rule and for expiration of the hard deadline. If either condition applies, withhold the answer and show the applicable source-unavailable or timeout message. Reviewer approval does not override these checks. |
| Supervisor run context | Runtime-supplied and read-only to the supervisor. Fields: run_id, project_id, and chat_id are UUIDs; question is a string preserving the original user question; eligible_dataset_ids is a list of UUIDs pinned at submission. Runtime checks source authorization and availability on dispatch. Actual source use is recorded separately in evidence. CLI supplies equivalent context without Django. Interpreted intent is separate from the original question. UUID version, serialization, and CLI ID conventions remain open. |
| Supervisor control decisions | The supervisor selects work through pending_tasks and the runtime dispatches the queue head into current_task. The graph determines what to execute from the actions in current_task. Action types and recorded outcomes drive the transitions, including graph-enforced mandatory review after a fresh draft. A separate routing decision field is unnecessary. An action that pauses or ends the run must be the sole action in its task, so it cannot interrupt sibling actions. Before dispatch, the runtime validates the proposed task. If the task is invalid, the runtime rejects it before any action starts and tells the supervisor which rule it violated. The supervisor can repair the plan within its normal decision budget. If that budget is exhausted, follow the agreed stopping rules. Concrete task and action schemas, remaining validation rules, and the validation error format will be defined with the relevant components. |
| Supervisor decision inputs | For each decision, give the supervisor the original question, relevant conversation context, metadata for eligible datasets, the pending plan, bounded summaries of action outcomes, and the remaining run budget. This defines the decision input, not additional persisted state fields. The memory design owns conversation context assembly. |
| Supervisor evidence reuse and routing examples | Reuse prior evidence for a direct answer only when it supports the requested claim under the same dataset snapshots, metric definition, filters, period, and level of detail. Use few-shot examples in the supervisor prompt to demonstrate matching evidence reuse, fresh analysis when evidence is incompatible or insufficient, and clarification when ambiguity materially changes the answer. Ask for clarification only when the question and confirmed context leave a choice unresolved and choosing among plausible interpretations could materially change the answer. If plausible interpretations lead to the same substantive answer, proceed. Design the prompts, including the few-shot examples, after the component designs are complete. Refine the examples using routing evaluations. |
| Supervisor execution boundary | The supervisor coordinates work without executing SQL or Python itself. It may inspect available dataset metadata and retrieve context. SQL and Python execution belong to their specialists. |
| Supervisor model | Use a bounded ReAct-style supervisor for routing, planning, and delegation. It can answer general questions, reuse verified context, or call SQL, Python, reviewer, and clarification specialists as needed. Code enforces tool access, run budgets, and completion checks. This supersedes the separate Router Agent design. |
| Supervisor completion state | Do not add a separate requested_outcomes field to supervisor state. Before answer handoff, the supervisor checks the original question against outcomes and remaining work in pending_tasks. An empty queue alone does not establish completion. The representation of confirmed definitions and filters remains open for memory and task-contract design. |
| Supervisor action model | Represent actions with a Pydantic Action model as well as the already agreed Task models. The shared Action fields are action_id (UUID) and type (the action discriminator). Concrete discriminator values, specialist-specific payloads, and any action subclasses will be defined with the concerned components. How terminal and clarification actions record outcomes and transition the graph is a pending design decision. |
| Supervisor outcomes | Use outcomes, a dictionary keyed by action_id. Each key holds the latest recorded outcome for that action. A task completes when each of its action IDs has a terminal outcome for the current dispatch, including failures and timeouts. Preserve successful sibling outcomes and retry only the failed action when a retry is warranted. Use at-least-once crash recovery: reuse checkpointed outcomes and replay unresolved actions when eligible. An action may have run before its outcome was saved, so make replayed effects idempotent or deduplicate them with a stable action identity. Keep action_id stable and give each deliberate retry after a recorded failure a new attempt number. The runtime accepts outcomes only for the expected attempt and checks task completion against that attempt. Crash recovery replays an unresolved attempt with the same number so effects can be deduplicated by action ID and attempt number. Supervisor state keeps the latest outcome and expected attempt number for each action. Keep earlier attempt history in traces for debugging, subject to the agreed trace data rules. Exact outcome fields and replay mechanics remain open. |
| Supervisor task models and outcomes | Task model decision: define a Pydantic task base class and subclasses for different task types. pending_tasks contains only waiting tasks. Its first entry is next. On dispatch, the runtime moves the full task from the head of pending_tasks to current_task. After all actions have recorded outcomes, the runtime clears current_task and the supervisor reassesses the queue before another dispatch. Detailed recovery and retry mechanics remain open. Concrete task payloads and polymorphic validation and serialization remain open. |
| Supervisor task terminology | A task groups independent actions that may run concurrently. The supervisor can revise the ordered pending_tasks queue between dispatches. The outcomes dictionary keeps completed action outcomes separate from pending and active work. Direct answer, clarification, and answer handoff contracts remain open. |
| Supervisor task plan | The supervisor can add, revise, reorder, or remove pending tasks between dispatches within run limits. A task can run only when its prerequisites are satisfied. Apply the existing retry policy to a failed prerequisite action. If it succeeds on retry, dependent work can proceed. If the action is ineligible for retry or its retries are exhausted, the supervisor uses the failure in outcomes to revise the plan. Before dispatch, the runtime blocks a queue head whose required results are missing and returns control to the supervisor. This prerequisite check does not trigger a retry. Keep outcomes separate from the queue so replanning preserves gathered evidence. Exact dependency tracking and checkpoint behavior remain open. |
| Parallel delegation | At each action step, the supervisor can batch independent specialist tasks in parallel and re-plan after observing their results. Dependent tasks wait for their inputs. Runtime capacity and a shared budget constrain execution. The supervisor can invoke the same SQL specialist multiple times for independent tasks. The concurrency limit is still open. |
| Run independence | Each submitted question has its own run state. Linked clarification replies resume the original run. New questions create new runs. |
| Direct answer | Combine general explanations and answers from existing evidence into one Direct answer path. The supervisor can compose it in the same model call. Keep general-knowledge and evidence-based trace labels distinct. Data claims require verified evidence. |
| Clarification Agent | Ask a focused question when a run needs user input. Show a question card inside the Chat with suggested answers where useful and a field labeled Reply to clarification. Save progress and release the worker and sandbox while waiting. A reply through the card resumes the same run with its recorded Dataset scope. Keep the main composer available with the label Ask a new question and send its messages to the supervisor as new turns. |
| Agent behavior | Profile data before analysis. Check join cardinality, analysis grain, units, date windows, and denominators. Verify numeric claims against evidence and require an Answer Specialist draft and Reviewer approval, with at most two review passes total. Carry agreed definitions and filters into follow-ups while invalidating context from removed sources. Route simple analyses to SQL and call Python when the task needs it. Benchmark routing and reviewer settings. |
| Answer and review workflow | Fresh analysis goes from evidence gathering by the supervisor to an Answer Specialist, then the Reviewer. Approval permits display. Missing or incorrect computed evidence goes back to the supervisor. If evidence is sufficient, a draft calculation or conclusion error goes back to the Answer Specialist. The run allows two review passes total, including the initial review. A second rejection ends with a brief explanation of the unresolved issue and omits the rejected analysis. If evidence is missing, state which claim lacks support and what evidence is needed, based on the reviewer findings. This supersedes the earlier single-correction policy. When a review finds both evidence issues and draft errors, evidence issues take precedence and the run returns to the supervisor, subject to the two-pass limit. The reviewer reports only blocking problems with correctness, evidence, or fulfillment of the request. Wording and style preferences remain with the Answer Specialist. |
| Tool guardrails and adversarial evaluation | In 1D, treat instructions embedded in uploads as data and enforce the run's authorized data scope at the SQL and Python tool boundary. In 1F, evaluate embedded instructions, an attempt to read an out-of-scope file, and an unanswerable data question. The expected outcomes are treating the cell as data, blocking the read, and explaining the missing evidence. |
| Checkpoints | Use Redis-backed LangGraph checkpoints. Save reusable outputs separately so a new worker can reconstruct state after interruption. Recovery cannot restore unsaved sandbox state. |
| Run controls | Show the current stage, enforce a run time limit, and offer Retry for eligible failures using the original Dataset IDs. Use a valid checkpoint for recovery. Defer a manual Stop action in v1. |
| Evaluation | Run the evaluation suite through the CLI. Compare single-agent and specialist configurations against shared fixtures and safety requirements. Use a held-out suite for final comparison. Measure correctness, latency, and cost to choose the configuration. |
| Constraints | Aim for a 4–6 week build once design is complete. Budget model and sandbox usage for local runs and evaluations. The showcase is local-only. AWS hosting and continuous deployment are outside scope. |
| Deferred scope | An LLM gateway, semantic caching, a separate Streamlit interface, and the detailed cohort walkthrough. |

## Working terminology

| Term | Meaning |
| --- | --- |
| **Project** | The user's container for datasets and chats. |
| **Dataset** | A fixed snapshot of one supported uploaded file added to a Project. A workbook or SQLite upload can expose multiple tables. |
| **Chat** | A conversation within one project. |
| **Analysis run** | One attempt to answer a chat question, including any recovery of that execution. |
| **Run scope** | The Datasets eligible for an analysis when its question is submitted. |
| **Used sources** | The Datasets that a completed result actually relied on. |
| **Clarification reply** | A response to an agent question that resolves ambiguity in a waiting analysis run. |
| **Evidence** | Inspectable computed results that support an answer. |
| **Artifact** | A saved output, such as a result table or chart. |



## PRD baseline

`PRD.md` records the agreed scope, demo flow, milestones, and showcase acceptance criteria. The remaining design work is in the architecture and module specs.

Use `architecture.md` for service boundaries and infrastructure decisions.

The intended supervisor context includes bounded recent chat turns, a summary of older conversation, and observations from the current run. Older original turns and verified results can be looked up in persisted Postgres records when needed. Exact selection rules, summary creation and refresh, and retrieval across different Chats remain open for the later memory discussion.

The ingestion spec will define how to report invalid JSON record shapes, conflicting field types, and unsupported Parquet column types.

## Deferred memory design discussion

Discuss memory for both the agent loop and the overall application in a later architecture round. Cover run state, recent conversation windows, older-history summaries, persistent original messages and evidence, checkpoint recovery, and Chat versus Project memory scope. Decide how summaries are generated and refreshed, what retrieval tools expose, how specialist context is assembled, and how source removal invalidates derived memory. Original evidence remains the basis for data claims. Summary and retrieval mechanics are still open.
## Architecture discussion process

Work through the standalone agent first, then each remaining development phase in depth. Use flowcharts, concrete examples, and explicit tradeoffs. Record confirmed decisions as they are made.
