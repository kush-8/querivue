# Database and storage architecture

**Design approved and planning closed, 25 November 2026.** This guide owns the Phase 2 database/storage contracts. See the [closure and remaining gates](../memory.md#database-and-storage-planning-closure--25-november-2026). Agent behavior and its canonical record contracts remain owned by [Agent integration](agent-integration.md#persistent-recovery-and-concurrency), [ingestion](data-ingestion.md#ingestion-integration-contract) and the component specifications.

## Status and boundaries

Approved in the opening review: a Django-owned Postgres adapter/migrations; relational ownership and dependency records alongside exact binary payloads; private shared-volume files whose visibility is ledger-controlled; immediate deletion revocation with deferred safe cleanup; atomic successful replacement. The independent agent retains standalone SQLite. Earlier approvals already require one authority, immutable Dataset IDs, frozen conversational bases, guarded publication and reconstructible Redis projections.

The user approved the concrete schema/ownership constraints, locking strategy, Chat/result deletion rules, replacement conflict behavior, adapter operations and migration/acceptance packet. Design approval does not establish implemented or measured storage readiness. API routes, broker/job delivery, UI and worker/checkpoint integration retain their later phase owners. No account system or public signup is introduced for the local single operator.

## Ownership and adapter boundary

Django models/migrations own one application database, including the agent ledger tables. Put the Postgres adapter in the backend; the agent package imports no Django model/settings. Shared domain validators and the framework-free authority operation contract own policy. Each adapter implements the operation's atomic read/check/write boundary. Do not split one operation into independently committed repository calls or implement different admission/publication rules for SQLite and Postgres.

Current agent Authority imports concrete SQLite Ledger/LedgerOps. Extracting a storage operation boundary and adding conformance fixtures is prerequisite implementation work, not an existing plug-in capability. An ORM transaction around a separate SQLite connection is not a shared transaction. Application operations compose agent transitions using the same Postgres connection/transaction; nested operations join it and never independently commit. Pure immutable payload validation/hash preparation can precede locking, but current authorization/revisions/deadlines are always rechecked inside.

Initially use one Django domain app with focused model/service/adapter modules. Physical module names are implementation choices; adding a second migration owner or independently writable run store is not. Normal callers use services/authority operations, including deletion; admin/bulk model deletion must not bypass them.

A direct Postgres-driver adapter inside the independent package was considered. Keeping the adapter with Django lets application writes and agent transitions share its connection/transaction and migration owner. A Django-free Postgres CLI is not a current requirement; standalone SQLite remains available. Simultaneously writable application Postgres and agent SQLite stores are excluded by the single-authority contract.

## Physical records and relationships

Every domain identity is a UUID primary key, preserving the existing runtime UUIDv4 minting and canonical lowercase wire form. Add an owning Project column to domain rows, plus Chat/run/Dataset ownership where applicable. Native timestamps are UTC operational indexes; exact user/source temporal representations stay in canonical payloads. Mutable lifecycle rows have nonnegative expected revisions; immutable payload content never changes in place except authorized erasure into a distinct tombstone state.

The following names describe approved table responsibilities; exact module and SQL identifier spelling can be settled during implementation. Existing strict contract fields are reused, not replaced by a new generic JSON schema. Nonnullable scope columns are required where listed; explicitly optional references below use null rather than fabricated IDs.

### Database constraints and indexes

Keep simple UUID primary keys for normal Django relationships. Add unique referenced tuples and database composite foreign keys for same-owner relations: (project, chat); (project, dataset); (project, chat, run); (project, dataset, snapshot); and typed record/producer relations. A Run must reference its actual owning Chat; a RunSource's snapshot must belong to its Dataset and Project. Optional tuple components require explicit checks: run implies Chat, snapshot implies Dataset, and a ready pointer implies the published own snapshot. No nullable tuple may accidentally skip an ownership constraint for a populated child ID.

Django 5.2 ForeignObject does not create these database constraints. Use explicit named, reversible Django RunSQL migration operations for additional composite foreign keys, retaining ordinary model foreign keys and model-state consistency. This is not a change to composite primary keys. Inspect generated SQL and PostgreSQL catalog constraints in acceptance; no application-only check or CHECK subquery is substituted for cross-row ownership. Avoid cascade deletion of domain content; restrictive foreign keys plus deletion services preserve fences/accounting until cleanup is safe.

Enforce existing unique keys: intake/admission chain; action/expected attempt outcome; logical invocation and physical request; operation mapping and incarnation; (run, review_pass), terminal verdict; accepted analytical reply per question; progress application per cycle; terminal publication per run. A duplicate returns the existing committed result only after exact scoped identity/content comparison. Concurrent inserts resolve through a uniqueness conflict and guarded reread, never by overwriting content.

Index foreign-key lookup columns explicitly, reverse SourceDependency(dataset, snapshot, record), reverse RecordDependency(input, derived), RunSource(dataset, run), ChatVisibility(chat, sequence), pending delivery/cleanup state, run owner/deadline and active preparation. Add broader JSON/GIN or query indexes only when a measured query needs them. ContentRecord canonical bytea remains authoritative; optional JSON/text projections are reconstructible and lossless encoding is required for unsupported PostgreSQL text characters. PostgreSQL jsonb does not preserve exact JSON representation and rejects the Unicode NUL escape; storage must not narrow the canonical contract. Official-source notes are below.

## Transactions, concurrency and read access

Use default READ COMMITTED with explicit row locks and conditional writes. Initial local operation uses a coarse Project guard for all authoritative mutations. Lock order is: enclosing operator accounting guard when needed → Project → Dataset rows in UUID order → Chat rows in UUID order → Run rows in UUID order → child/resource rows in fixed table/key order. Project deletion can revoke the Project without eagerly updating every child; reconciliation follows. A transaction discovers all earlier-tier guards before acquiring later-tier locks; if dependencies changed, roll back and retry rather than lock backwards. Child creation and reference registration follow the same Project guard, including cleanup and import.

This serializes short metadata changes within a Project, not provider/sandbox execution or entire Chat runs. It is simpler to audit for the single operator; finer lock granularity is a future measured optimization. No file/network/Redis/provider work or user wait occurs under those locks. Expected revisions, current generation/lease, phase, source status, hard deadline and budget checks still apply despite serialization.

Database timeouts and a finite transaction retry policy must be resolved in the executable configuration before enablement; earlier unapproved timing proposals are not accepted here. Retry only the rolled-back database operation, preserving its identity and rereading guards. Never retry external dispatch as a side effect of a database retry. An unknown commit outcome is resolved by querying the stable operation key before considering another transition. Missing configuration, unknown authority or irreconcilable clock state blocks effects.

| Operation | Guarded atomic change and recovery rule |
| --- | --- |
| Receive upload | Reserve declared size before accepting bytes; for unknown lengths reserve each bounded increment before writing it. Count retained failed/staged uploads plus pending reservations. Finish by checking exact length/hash and associating the same upload identity; preparation retry cannot double charge. Oversize or conflicting replay publishes no Dataset. |
| Start/confirm preparation | Validate upload/settings and current Dataset state; reserve attempt capacities, allocate current attempt/generation and dispatch identity together. Changed confirmed settings fence the old attempt. Inspection waiting releases the sandbox. |
| Publish Dataset / replace | Persistent complete bytes must already verify. Commit own snapshot/catalog/profiles, ready pointer and one readiness delivery together. For replacement also lock/check the live original source, tombstone it and revoke affected runs/records in the same transaction/conflict domain. If original was already removed or replaced, candidate publication fails with a source conflict; do not silently reinterpret replacement as Add. Original stays usable on failed preparation. |
| Receive question / admit | At receipt lock Chat to freeze its current visibility cutoff and explicit target, allocate a receipt/message event and persist exact input/idempotency. Entry runs outside locks. At admission revalidate ready/source eligibility, record immutable RunSource rows and original received basis/configuration, attach initial charges and create exactly one run. A cutoff grants no source access. |
| Publish Chat-visible record | Allocate next Chat sequence only on committed visibility; a late result gets a later sequence, not the originating submission's position. Reads for an earlier run honor its stored cutoff and exact linked supplements. Later state cannot rewrite that basis. |
| Dispatch / adopt / finalize | Apply existing immutable mapping, physical accounting, retirement, review and publication rules in one adapter operation. Tombstone/source and owner guards are read inside the transaction. Commit replayable delivery alongside the state change; on_commit is only a wake-up optimization. |
| Clarification reply | Match exact active question/wait/expiry and original run; entry acceptance, linked charges, one accepted-reply claim and resume readiness commit together. Lost acknowledgment reads that same claim. Competing content cannot overwrite it; new composer submissions remain independent. |
| Delete / revoke | Commit owner/source/record revocation and cleanup intentions first. Guarded reads stop relying on affected records immediately, even before child status projections update. In-flight external work is fenced; retirement remains owed. |
| Cleanup | Claim a stable intent under guards and prove references/active transfer/incarnation conditions permit removal. Mark storage object deleting so it cannot gain new live bindings; erase bytes outside the transaction; then acknowledge idempotently. Crash after unlink but before acknowledgment repeats safely. Missing bytes are acceptable only for an already revoked cleanup target, never a live evidence object. |

Public result/card/artifact reads resolve committed IDs through an authorized storage service, checking Project/Chat lifecycle, record usability and all source/record dependencies. A storage UUID or digest alone grants no access. Open and serve only verified immutable bytes through bounded reads; stream authorization is rechecked at bounded chunk boundaries and stops on observed revocation. Do not hold a database lock for a response stream. Authorization committed before deletion may already have delivered/buffered bytes; no recall is promised. New opens after revocation fail. API phase must preserve these rules for download, range requests, caching and status/result responses; no static MEDIA_URL or permanent file URL bypasses them.

## Deletion, retention and file layout

Dataset deletion follows the approved source-union policy, regardless of RecordDependency reachability. Every unfinished pinned-scope run becomes unusable even if it has not read the Dataset. Completed source-dependent records revoke; independently scoped records remain. Replacement IDs never revive old scope or dependent records.

**Approved Chat and result deletion:** Chat deletion revokes its messages, memory, generated outputs, runs and work, but leaves Project Datasets and their independent ingestion profiles. Cross-Chat analytical retrieval is already prohibited. Deleting a single result preserves the user's question and Project sources, revokes that publication and its run-produced evidence/code/charts, and follows RecordDependency edges to revoke later materializations that retained those inputs. Independently computed later results remain usable. This prevents a deleted answer surviving through a copied summary or derived answer. Unfinished consumers stop; this is an access/deletion effect, not a new manual Stop feature. The API/UI phase decides confirmation/display wording, not weaker storage semantics.

Record/blob reference checks distinguish ownership from reuse. Revoked content cannot remain accessible merely because another result references it; dependents revoke first. Independent Project profile bytes are not owned by a deleted Chat/result. Ingestion source removal governs them. Content erasure removes packets, requests/responses, SQL/code, derived memory, files and checkpoint/cache content under the affected ownership/dependency closure, retaining only minimal non-content tombstones/accounting/retirement obligations. IDs and hashes remain access-controlled and are not presumed anonymous. Tombstones cannot replay erased content.

Keep the initial revocation transaction bounded: commit the source/Chat/Project or run-generated-content revocation marker and durable reconciliation intent. Reads/adoption consult live owners and source/record ancestors, so delayed descendant enumeration cannot leak revoked content. Enumerate and erase descendants in bounded batches outside the initial transaction. An incomplete dependency check or exceeded lookup budget denies use rather than assuming eligibility. Cleanup must preserve enough non-content dependency/tombstone structure to finish this traversal before removing those rows.

Raw Project quota is logical retained upload bytes plus pending reservations. Explicit deletion releases that logical charge once; physical storage stays charged to retained-resource accounting until confirmed cleanup. A replacement must initially fit old plus new raw uploads. Separate physical prepared/evidence/quarantine caps also gate allocation; delayed retirement is not an opportunity to exceed them. Accepted failed uploads have no automatic TTL. Abandoned unadmitted transfers need an approved finite cleanup policy and inactive-owner proof before their capability is enabled; no 24-hour setting is silently approved.

Use this private layout on the shared persistent volume: `quarantine/<project_uuid>/<staging_uuid>/` for active transfer candidates, and `objects/<project_uuid>/<storage_uuid>` for sealed immutable blobs. These server-derived paths are not public contract fields; public ArtifactRef retains its UUID storage_ref. Original filenames, SQL identifiers and model text never form paths. Exact packets/canonical small records can remain bytea; large typed artifacts stay outside the database. Verify containment, symlink/reparse/device restrictions, exact bytes/hash/size, closed DuckDB/WAL state, file and directory durability on the actual volume before publication. Do not rewrite or share bytes across owners merely because hashes match.

Track staging ownership before transfer; reconciliation may find unregistered crash candidates, but deletes only after consulting current ledger refs and active writers/retirement. Disk full/permission/transfer/hash failures publish nothing and produce bounded diagnostics. A missing/corrupt committed blob reports integrity/unavailability and is not recomputed under its old identity. An idempotent reconciler handles pending delivery, stale staging, revoked content, checkpoint invalidation and physical cleanup; worker scheduling is assigned to its later phase, with a local management-command entry point for storage acceptance.

## Application integration and SQLite handoff

Phase 2 supplies persistence and the adapter; it does not move the agreed standalone milestone to Django or claim standalone completion. Migration is a separately executable, offline maintenance operation after compatible standalone records and the Postgres adapter pass their gates:

1. Enter maintenance mode and quiesce all dispatch/intake/publication writers, including CLI processes. Record source schema/codec/configuration identity and an export identity. Reconcile external executions; unresolved work stays fenced with preserved retirement/accounting records, and no affected capability resumes without its required proof.
2. Create/apply Django-owned schema migrations to a non-serving target. Export a consistent SQLite view plus all live/tombstone records and referenced immutable bytes; preserve IDs, source/record dependencies, sequence cutoffs, owner generations, budgets, timers and canonical digests. Do not import only successful runs or omit minimal operational tombstones. Unsupported source schema/records block import with a bounded report.
3. Idempotently import under the export identity, with stable source IDs and exact content matching. Rebuild query projections from canonical records. Validate row/key coverage, ownership, uniqueness, dependency completeness, blob hashes and all canonical compatibility vectors. Quiesced copy/reconciliation keeps deletion policy consistent; staging backups are private and removed under the same policy after acceptance.
4. Fence prior owners, conditionally select the sole Postgres authority in operator configuration and start only compatible runtimes. All old writer processes must be stopped before switching; seal the former SQLite store read-only to the runtime and keep it out of active configuration. Compatible runtimes verify authority identity at startup and before effects; an old configuration cannot authorize a second writer. Redis state is verified/rebuilt as a projection of the same run IDs/revisions; old checkpoints cannot override migration. Perform fresh-process scripted recovery using the original scope and remaining budgets before enabling effects.
5. Before target receives new authoritative writes, a failed validation can abandon the target and retain SQLite as the sole authority. After target writes, never roll back by reopening the stale SQLite copy; remain on Postgres or perform a separately quiesced, verified reverse migration. Preserve proof of the authority switch and deny outdated processes.

Local Postgres and file data use distinct named persistent volumes; restarting containers must not recreate empty storage silently. Migration/application connections use explicit environment configuration with credentials out of source/records/digests. Keep the existing Django 5.2 line for this design; exact compatible server/driver/container identities and finite connection/lock/statement settings are frozen by the implementation task before service enablement. No current-server version or eventual hosted compatibility is inferred from documentation URLs. Ordinary startup applies schema checks, not destructive resets or automatic content migrations.

No automatic backup service is added. A manual backup/export needs a quiesced consistent ledger/file set, private deletion-aware lifecycle and a restore verification before it can be advertised as recoverable. Restoring old bytes cannot undo a later deletion or make an obsolete authority active. Define any future online backup mechanism separately.

## Operation results and implementation slices

The adapter exposes typed command receipts, using the existing domain identities and strict contracts: create Project/Chat; reserve/finish upload; start/confirm preparation and commit its candidate; record/admit intake; read eligible Chat context at cutoff; claim/renew run; commit existing authority transitions; authorize/open result/artifact; revoke Dataset/Chat/result/Project; reconcile delivery/cleanup; export/import maintenance state. Every mutating command supplies stable request identity/digest, scope and expected revisions; runtime transitions additionally supply OwnerFence and their existing timer/accounting inputs. Exact Python signatures adapt to the extracted framework-free contract during implementation without changing these atomic boundaries.

Failures distinguish duplicate success, content identity conflict, stale revision/owner, source unavailable, expired/not eligible, quota/capacity denial, bounded lock contention, integrity failure and unavailable storage. Retryability is explicit; no automatic new run, fresh budget, source rebinding or external redispatch. User-facing whole-run Retry policy/identity remains owned by the API phase and must preserve original inputs and unresolved retirement barriers. Component action retries keep their already approved identity/attempt rules.

| Implementation slice | Required focused acceptance |
| --- | --- |
| S1 adapter contract and migrations | Shared SQLite/Postgres operation fixtures; migrate fresh database and inspect named ownership/uniqueness constraints; direct invalid inserts fail; exact canonical binary round-trip including Unicode/NUL, decimals, temporal offsets and negative zero. |
| S2 Project/upload/preparation persistence | Concurrent raw quota reservations cannot jointly exceed cap; idempotent transfer/retry, failed upload retention, competing attempts, full snapshot readiness and both replacement publication/deletion orders. Deterministic trusted fixture bytes suffice for storage proof. |
| S3 Chat/intake/run ledger | Receive cutoff versus late completion, one admission/reply/publication, no cross-Chat scope, stale coordinator denial, atomic shared accounting and replays after lost acknowledgments on separate Postgres connections. |
| S4 storage access and erasure | Private authorized reads, no raw-path bypass, corruption and disk/transfer failures, Dataset/Chat/result/Project revocation closure, independently computed survivors, retirement/reference-guarded cleanup and crash after file removal. |
| S5 maintenance handoff and persistence | Quiesced export/import/replay without digest/ID/budget changes; missing/unsupported records fail; authority-switch fault injection, restart with original source scope, persistent volumes and no stale-store rollback. |

Use actual Postgres concurrent transactions and independent connections for locking evidence; Django tests that implicitly wrap a transaction are insufficient on their own. Keep model/sandbox transports scripted unless separately authorized. API phase owns HTTP validation/download/cache behavior; worker phase owns durable delivery scheduling; checkpoint integration owns background restart proof; backend integration owns combined real-flow failures. Exact environment/configuration freezing is an implementation enablement gate. No paid/live provider or sandbox operation follows from design approval.
